# 裁定先例台帳（human_reference 350セルレビュー）

境界事例の裁定を記録し、以後の同型セルに機械的に適用する。noteには先例トークンを書く。
camera-readyでは各裁定を感度併記の対象とする。親質問は常に:
「この記述は、会議を欠席した読者にそのロールの答えを与えるか？」

## 先例1: `prior-stage-boilerplate`（確定 2026-09-11, batch 1）

- **対象**: Denver系定型句 "The Committee approved filing this bill/item at its meeting on <date>"
  など、**サンプルされたセッションより前の、別会議体による手続き行為**の記述
- **裁定**: O の Topic Gate に**数えない**（Presence 0.0 側）
- **根拠**: Oの測定目的は「このセッションでどう処理されたか」を読者に伝えたか。前段階の
  提出承認はその答えを与えない。gateのstage寛容条項（"exact stage ... not evaluated"）は
  セッションの処分の記述の段階ズレへの寛容であり、別の実在イベントの記述をcreditする
  趣旨ではないと解する
- **感度報告**: creditした場合のO Presenceも camera-ready で併記する
- **確認事実**: 生成要約3,320本にこの定型句は出現ゼロ → 本実験の数値には影響しない

### 先例1の適用範囲の拡張（2026-09-11, batch 1, 01B）

前段階の手続き記述（filing承認等）は **B にも数えない**: agenda-setting background の
Quality Gate（connected_to_agenda_necessity）が要求する「議題の由来への接続」を持たないため。
適用スロット: O, B。

## 先例2: `in-session-event-not-B`（確定 2026-09-11, batch 1, 01B）

- **対象**: サンプルされたセッション**当日中**の出来事の記述（当日の修正 "Amended <当日日付>"、
  採決、可決など）
- **裁定**: これらは O / N の材料であり、**B（事前の背景）には数えない**。meeting IDの日付と
  記述中の日付の一致で機械的に判別できる
- **根拠**: Bの問いは「なぜこの議題が出てきたか」。セッション内で議案がどう扱われ・どう変わったかは
  その答えではない。Bゲートの語彙 "revision" は事前の改定経緯を指す

## 先例3: `recommended-disposition-not-O`（確定 2026-09-11, batch 1, 05O）

- **対象**: Long Beach系定型 "Recommendation to declare ... read and adopted as read" など、
  **事務局起案の勧告文の中に現れる処分語**（declare adopted / approve / authorize 等）
- **裁定**: これは「提案された処分」の記述であり、「会議体が処分を行った」という記述ではない。
  **O の Topic Gate に数えない**（Presence 0.0側）
- **根拠**: "Recommendation to X" はセッション前に事務局が書くアジェンダ件名（稟議の件名に相当）。
  引き継ぎの読者は、これを読んでもセッションの結果（可決されたか）を知れない。
  実際の処分は議事録のaction line（この参照には含まれない）に記録される
- **注意**: 先例1（別会議体の過去の実在手続き）とは型が異なる別先例。実務上ほぼ確実に可決される
  案件でも、text-says原則により文が表現していない処分は数えない

## 先例4: `scope-token-two-part-rule`（確定 2026-09-11, batch 1, 05N）

- **対象**: N の QG scope_boundary に対する、地名・範囲トークンの扱い
- **裁定（二部構成）**:
  1. **法令・機関の名称内の地名**（"Long Beach Municipal Code" の Long Beach 等）は
     **識別子であり、scope_boundaryに数えない**（条項番号=識別子と同じ原則）
  2. **明示的な適用範囲タグ**（"(Citywide)" / "(District 2)" 等）は、payloadの
     **geographic scope_boundary として数える**
- **帰結**: Long Beachキャプションはほぼ全件が末尾に適用範囲タグを持つため、payloadを
  伴うLong Beach物件のNはこのタグでQGが立ちやすい。系統的な効果として認識した上での裁定
- **注意**: タグが立てるのは scope_boundary のみ。TG（payloadがアクションに付随して
  存在すること）は独立に必要

## 先例5: `surface-variant-not-contradiction`（確定 2026-09-11, batch 2, 09T）

- **対象**: 固有名詞・番号等の表記揺れ（"Avery & Associates" vs "Avery Associates"、
  &/and、法人格表記、略称、綴りの微差）
- **裁定**: 実体の同定に支障がない表記揺れは **Fact Check の矛盾に数えない（FC=1側）**
- **根拠**: FCの基準は「明示的な矛盾のみエラー」。矛盾は主張レベル（別の実体・別の内容・
  別の結果を伝える）でのみ成立し、表記のバリエーションは主張を変えない

## 先例6: `ceremonial-praise-not-N`（確定 2026-09-11, batch 2, 06N）

- **対象**: 式典系（proclamation / 表彰・追悼・感謝）の称賛内容（功労年数、業績列挙など）
- **裁定**: 称賛の記述はNの操作的payloadに数えない。数字（18年等）が含まれていても、
  それは称賛内容の事実であり、アクションが運ぶ条件・要件・範囲ではない
- **根拠**: Nゲートのnot_match「称賛のみの場合（不成立）」が正面から規定。
  IAA hardサブセットの境界カテゴリ ceremonial_proclamation_N と同一論点

## 先例7: `review-object-not-auto-B`（確定 2026-09-12, batch 4, 15B）

- **対象**: 再審・不服申立て・上訴型の議題（Call for Review / appeal）における、
  再審対象（先行の却下・決定）の記述
- **裁定**: 再審対象の存在はTGを満たしうる（先行却下は事前の出来事）が、
  **議題が再審であるという構造それ自体はQG（背景が議題を形作った関係）に数えない**。
  QG成立には再審の precipitating context（誰が請求したか・根拠・変化した事情）が必要
- **根拠**: 再審対象は議題の目的語であって背景ではない。構造だけで通すと全再審案件が
  自動的にB成立となり、対象と背景の区別が消える（Citywide/何でもあり歯止めと同型）

### 先例7の適用範囲の拡張（2026-09-18, batch 7, 24B）

再審対象に限らず、**行為の目的語**一般に適用する: 謝罪・非難・承認等の対象として
タイトル・実行部分に埋め込まれた事実（"Resolution to ... Apologize for the Role Played by
the City of Boston in the Trans-Atlantic Slave Trade" の「役割」）は、語句として要約中に
存在しても**背景事情の記述として述べられたことにならない**（TG不成立側）。
背景としてcreditするには、目的語の外で背景条件として記述されている必要がある。

## 先例8: `out-of-segment-action-line`（確定 2026-09-18, batch 7, 27O/27N）

- **対象**: 参照キャプションが、**判定対象としてサンプルされたtranscript区間の外**で起きた
  同一議案の処理（本会議での修正動議可決・本体否決 "Motion Prevailed; yeas 12" /
  "did not Pass; yeas 5, nays 7" 等）を記述しているケース。区間内の状態はゲートの
  FC valid項目が定める（27では「委員会に留保・区間内採決なし」）
- **裁定（二部構成）**:
  1. **Presence側（27O）**: 区間外の処分記述はゲートのmatch行に現れない（ゲートは区間内の
     世界で書かれる）ため、text-vs-gateでmatch不成立なら **TGは通さない**（Presence 0.0側）。
     実在の出来事でも、判定対象区間の処分の答えではない
  2. **FC側（27N）**: 区間外イベントの追加報告（$10M→$5M修正、否決）は、区間内payloadの
     正確な記述（$10M要請）を**否定しない限り矛盾に数えない**（FC=1側）。処分・未了性の
     食い違いはO/Uの領分であり、FCのスロットローカル原則を維持する
- **根拠**: 採点の接地はサンプル区間。参照キャプションは議案単位で書かれるため区間外情報を
  運びうるが、これは参照というテキストタイプ固有の性質であり、ゲートの適用規則を
  区間接地から動かさない
- **メモ**: 先例1（別会議体の前段階手続き）の同族で、同一会議内・時間軸後方版。
  camera-readyでは先例1と併せて「参照キャプションの区間外情報」として一括議論する

## 先例9: `proposal-terms-not-final-terms`（確定 2026-09-18, batch 9, 31N/32N）

- **対象**: 勧告・検討議題の定型（"Recommendation to award ..." / "Consider Directing Staff to ..."）の
  **中に書かれた条件・数値**（$3.5M上限・10年契約、3年間の除外期間等）が、セッション内で
  差し替え・撤回されていたケースのFact Check
- **裁定**: 提案・勧告の枠内で述べられた条件は「採択された内容」の主張ではないため、
  最終動議の条件と異なっていても**FCの矛盾に数えない（FC=1側）**。矛盾になるのは、要約が
  それらの条件を採択済みの行為として主張する場合のみ
- **根拠**: 先例3（勧告文は処分を主張しない）のFC側対応物。FC valid項目自身が
  「元のアジェンダ勧告は$3.5Mだった」「当初議論の3年は最終動議で置換された」と提案時条件の
  実在を有効事実として認めている。省略・部分はエラーにしないというFC原則とも整合
- **観察（camera-ready用）**: 参照キャプションのFC論点は事実誤りではなく、この
  「提案時条件 vs 最終条件の乖離」（先例8の区間外イベントを含む）に集中する

## 先例10: `document-metadata-identifier`（確定 2026-09-18, batch 9, 33B）

- **対象**: 受領・保管（receive and file）等の対象となる**文書の表題・日付に埋め込まれた
  過去への言及**（"Responses to Questions from the December 22, 2015 Study Session" 等）
- **裁定**: 文書の表題・日付は**識別子**であり、Bの背景記述としてcreditしない（TG不成立側）
- **根拠**: これを認めると「頭に日付が書いてある書類はすべて過去に繋がる」ことになり、
  対象と背景の区別が消える（先例7と同じ何でもあり歯止め）。先例4第1部（名称内トークン=識別子）の
  スロット横断への一般化
- **注意**: 日付・数値がNで拾われるのは識別子としてではなく、**アクションが運ぶ操作的条件**
  （契約期間、期限、金額、適用範囲）として機能する場合のみ。文書メタデータはNの自動加点でもない

### 先例4の適用範囲の拡張2（2026-09-19, batch 11, 40T）

制度・法人の固有名に含まれる**対象クラス語**（"Five Points **Business** Improvement District" の
Business）も識別子であり、target / scope の記述として数えない。制度の性質（BID=商業不動産への
賦課）から対象を導くのは制度知識の持ち込みで、text-says原則に反する。構造的根拠:
名称でtargetが立つならTG通過要約は全件QG target通過となり、ゲート自身のnot_match
（「対象を示していない場合」）が到達不能になる。camera-readyの感度併記対象。
